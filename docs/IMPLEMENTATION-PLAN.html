04 / Strategy

実装方針と代替案

横断的な安全基盤を先に固定し、その上で利用者価値を縦に完成させる。

DEC-301

安全基盤と縦断実装の組合せ

承認済み
種別
決定
規範強度
必須
適用範囲
Production V1の実装順序

追跡、観測、テナント境界、監査、冪等性、Outboxを共通基盤として先に成立させ、その後は画面、API、ドメイン、永続化、監査、試験を機能群ごとに縦断して完成させる。

理由と影響

共通安全基盤を後付けすると、全モジュールのデータ境界と例外処理を再実装することになる。

一方で基盤だけを長期間作ると、実際のユースケースが通らず、契約の誤りを検出できない。

両者を組み合わせることで、横断制約を一度だけ実装し、各機能群でその制約が実際に働くことを早期に検証できる。

代替案と不採用理由
案利点不採用理由再検討条件
全基盤を完成してから業務機能へ進む横断構造を先に統一できる。実ユースケースとの接続が遅れ、不要な抽象化と契約誤りを検出しにくい。法令または外部監査が業務実装前の独立基盤認証を要求する場合。
画面単位で先に作る見える進捗が早い。認可、監査、状態遷移、復旧の境界が画面ごとに重複し、サーバー側の正本が崩れる。採用しない。
全要件を並列に一括実装する多数の担当者を投入しやすい。共通契約の変更が広範囲へ波及し、未完成の依存をモックで隠す。共通基盤と公開契約が安定し、独立した作業境界をCIで強制できる場合。

コーディング原則の適用

設計原則と実装上の判定
原則適用レビューで拒否する例
DRYエラー契約、認可コンテキスト、監査、冪等性を共通化し、業務規則は所有モジュールへ一度だけ置く。同じ状態遷移をController、画面、workerへ複製する。
KISSHLDのモジュラーモノリスとPostgreSQL Outboxを維持する。必要性の計測なしにマイクロサービスや専用ブローカーを導入する。
YAGNIProduction V1とリリースゲートに必要な機能だけを実装する。クラウド移行や複数ノードを先行実装する。
SOLIDHTTP、アプリケーション、ドメイン、ポート、インフラの依存方向を固定する。ドメインがSpring、HTTP、他モジュールのRepositoryへ依存する。
デメテルの法則モジュール間は公開アプリケーション契約またはイベントだけを使う。他モジュールの内部クラスやテーブルを辿る。
GRASP状態と不変条件を情報を所有する集約へ置き、Controllerは変換と委譲に限定する。権限と状態判定を画面または汎用ユーティリティへ集約する。

フロントエンドの色、書体、余白、角丸、影は単一テーマへ置き、コンポーネント内へ値を直書きしない。

各画面はLLDのAPI応答を正本とし、業務状態や権限をクライアント側で推測しない。

05 / Roadmap

依存順の実装工程

各フェーズは前段の完了証拠を入力とし、未充足なら次段へ進まない。

PHASE 0 / START GATE

再承認と追跡基盤

製品コードへ入る前に、正本と機械検査を固定する。

入力

REQUIREMENTS 1.6.0、HLD 1.6.0、LLD 1.5.0、現行リポジトリ。

完了内容

三文書の承認、要件件数表現の一致、OPN-104の追跡CI、失敗fixture、保護ブランチ必須checkを整備した。

成果物

承認記録、追跡検査、失敗fixture、GitHub Actions成功、main保護設定。

完了条件

REQUIREMENTS、HLD、LLDの106要件が一致し、各失敗fixtureが統合を拒否し、実装開始が承認された。

Phase 0は2026-09-02に合格した。追跡必須checkが失敗した場合は、以後も変更を統合しない。

PHASE 1 / EXECUTABLE SKELETON

実行骨格と開発品質

既存の起動骨格へ、モジュール境界、Web、契約生成、観測の入口を追加する。

入力

Phase 0の承認済み契約と現行のbackend、deploy。

作業

Spring設定を一つのapplication.propertiesへ統合し、local／productionとapp／workerのprofileを排他的に検証する。その後、機械可読試験台帳、OpenAPI、パッケージ境界、アーキテクチャ試験、Flyway骨格、ReactとTypeScript、単一テーマ、OpenAPI生成クライアント、相関ID、health、metrics、traceを実装する。

成果物

起動可能なapplication、worker、web、空の業務モジュール、CI品質コマンド。

完了条件

環境と実行ロールの未指定・二重指定・不一致を起動前に拒否し、localの取得済み設定を本アプリ用keyで解決できる。全プロセスが秘密値を出力せず起動し、禁止依存をアーキテクチャ試験が拒否し、OpenAPI差分が0になる。

PHASE 2 / SAFETY SUBSTRATE

テナント境界、監査、冪等性、Outbox

すべての業務機能が共有する安全制約を先に成立させる。

入力

作業

認可コンテキスト、workspace複合制約、共通エラー、冪等キー、楽観ロック、監査append function、ハッシュ連鎖、Outboxリースと隔離、runtime guardを実装する。

成果物

共通ポート、DBロールとmigration、監査検証CLI、Outbox worker、拒否理由コード。

完了条件

越境、監査なし成功、二重副作用、順序逆転、評価不能時の許可を負の試験がすべて拒否する。

PHASE 3 / IDENTITY

認証、復旧、ワークスペース所属

後続機能が信頼できる主体、認証強度、認可世代を確立する。

主な正本

成果物

完了条件

10 / Rollback

ロールバックと前進修復

コード、DB、設定、公開状態を同じ方法で戻さない。

復旧手順

  1. 公開入口を閉じる

    外部trafficを保守表示へ切り替え、障害時刻、対象版、影響範囲を監査する。

  2. 戻せる対象を判定する

    アプリとWebは署名済みN-1へ戻せるが、DB schemaはNとN-1の共存契約が合格した場合に限る。

  3. DBを前進修復する

    contract前は切替flagと読取先を戻し、破壊済みschemaを逆変換しない。

  4. 秘密と認証を失効する

    影響したsession、client link、support grant、download grant、資格情報を失効し、旧値の復活を拒否する。

  5. 削除と失効を再適用する

    独立台帳をDB、公開射影、Valkey、S3、通知queueへ再適用し、件数とterminal hashを照合する。

  6. 閉域で再検証する

    読取、代表書込、監査、Outbox、認証、file配布、backupを確認し、全項目の合格後だけ公開する。

ロールバック先に失効前の秘密、危険な公開設定、暗黙の検査bypass、非対応schemaが含まれる場合はロールバックしない。

その場合は公開を閉じたまま前進修復する。
