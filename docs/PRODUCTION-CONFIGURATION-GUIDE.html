Production configuration runbook

本番設定値取得・設定マニュアル

一台のオンプレapplication hostから、既存オンプレ基盤とAmazon S3を安全に利用するために、人が取得・確認・記入すべき値を一件ずつ閉じる。

01 / Contract

先に守ること

この文書は値の取得方法を定める。実値や秘密そのものは正本HTML、Git、issue、chat、実行ログへ記載しない。

DEC-301

設定と秘密値の供給境界

承認済み
種別
決定
規範強度
必須
適用範囲
本番設定・認証情報

非秘密値は成果物内の単一application.propertiesを正本とする。管理者は秘密値だけを本番host上のGit管理外ファイルへ直接記載し、環境変数、repository、container image、Compose定義へ埋め込まない。

フェイルクローズ

未記入、placeholder、未知キー、所有者不一致、mode不一致、接続検証失敗が一件でもあればserviceを起動しない。MALWARE_SCAN_MODE=bypassだけは承認済みの明示状態であり、ClamAVへ接続せず警告・metric・監査を継続する。

02 / Files

03 / On-prem

オンプレ基盤の取得チェックリスト

既存基盤の担当者から専用接続点を払い出してもらい、汎用管理者資格情報を流用しない。

  1. 本番host識別情報と資源

    FQDN、固定IP、管理IP、CPU、memory、暗号化disk、空き容量、UPS停止閾値、NTP源、egress proxyを取得する。

    具体的な取得方法

    system管理台帳とBMC／hypervisorの一次情報を照合する。作業directoryは/etc/stageaccord。hostname --fqdn、ip -brief address、lscpu、free -h、lsblk -f、timedatectlを実行する。期待結果は台帳値との一致、時刻同期有効、秘密の出力なし。

  2. 公開DNS名とTLS証明書

    app、files、必要な公開host名、DNS A／AAAA、証明書chain、秘密鍵ファイルを取得する。

    具体的な取得方法

    組織のDNS／PKI管理者に正式FQDNと証明書を申請し、SANへ実際の全host名を列挙する。証明書は組織PKIまたは利用中CAの公式手順で発行する。openssl x509 -in <certificate-file> -noout -subject -issuer -dates -ext subjectAltNameで確認し、期待結果はFQDN一致、chain検証成功、有効期限監視登録済み。

  3. PostgreSQL専用DBとrole

    host、port、database、TLS root certificate、runtime username／password、migration username／password、接続元allowlistを取得する。

    具体的な取得方法

    DB管理者へapplication専用databaseとLOGIN roleを申請する。runtime roleへDDL、superuser、他database権限を与えない。接続文字列はjdbc:postgresql://<host>:5432/<database>?sslmode=verify-full。pgJDBCの公式SSL文書に従いhostname検証を有効にする。期待結果は専用schemaへの許可操作成功、他schema DDL拒否、平文接続拒否。

  4. Valkey専用ACL

    TLS endpoint、port、CA、username、password、専用key prefix、memory policy、backup方針を取得する。

    具体的な取得方法

    Valkey管理者へ専用ACL userとkey patternを申請し、管理command、他namespace、危険commandを拒否する。Valkey ACL公式文書に従いACLを設定し、TLS clientから許可keyのSET／GET成功、別prefixと管理command拒否を確認する。

  5. ClamAV接続点とscan mode

    stage-accord.malware-scan.mode、専用host、port、接続元allowlist、暗号化tunnel、定義更新責任者、timeoutを決める。

    具体的な取得方法

    当初はbypassを明示できる。requiredへ切り替える場合、ClamAV管理者が専用hostでclamdを構築し、application hostだけを許可する。clamd TCPは認証・暗号化されないため非信頼networkへ公開せず、必要なら専用VLANとstunnel等を用いる。公式clamd protocolのINSTREAMを使用する。期待結果はrequiredでEICAR検知、bypassでClamAV接続0かつBYPASSED監査。

  6. 監視・ログ・backup接続

    scrape先、alert送信先、log保管先、DB backup担当、復元検証先、保持期間を取得する。

    具体的な取得方法

    既存監視／backup台帳でownerと連絡先を確定し、外形監視はapplication hostと異なる障害領域へ置く。対象fileは監視側設定と配備台帳。期待結果は試験alert受信、秘密のlog出力0、隔離環境への復元成功、実測RPO／RTO記録。

04 / Amazon S3

Amazon S3の取得チェックリスト

「サービス名」ではなく、AWS region、4つのbucket名、用途別IAM資格情報を取得する。

  1. AWS accountとregion

    AWS account ID、運用region、請求owner、security連絡先を確定する。

    具体的な取得方法

    AWS Consoleのaccount情報と組織管理台帳を照合し、data residency、遅延、費用、利用可能serviceを基にregionを選ぶ。AWS CLIの作業directoryは任意の管理端末、対象profileは本番専用。aws sts get-caller-identity --profile <admin-profile>の期待結果は承認済みaccount IDとの一致。root userのaccess keyは作成しない。

  2. 4用途bucket

    quarantine、clean、preview、deliveryの世界一意なbucket名を確定する。

    具体的な取得方法

    公式bucket命名規則に従い、用途と環境を識別できる推測困難なsuffixを付ける。管理端末でaws s3api create-bucket --bucket <bucket> --region <region> --create-bucket-configuration LocationConstraint=<region>を各bucketへ実行する（us-east-1はLocationConstraintを省略）。期待結果は4bucketが同一regionに存在し、用途混在がないこと。

  3. 公開block・versioning・暗号化

    全bucketでBlock Public Access、versioning、default encryptionを有効にする。

    具体的な取得方法

    Block Public Access、versioning、暗号化の公式手順に従う。get-public-access-blockの4値がtrue、get-bucket-versioningがEnabled、get-bucket-encryptionが意図した方式であることを確認する。期待結果が一つでも異なれば起動不可。

  4. 用途別IAM policyとaccess key

    application、worker、download gatewayを分離し、必要なbucket／prefix／actionだけを許可する。

    具体的な取得方法

    IAM公式best practicesに従いrootと管理者keyを禁止する。オンプレからの長期access key採用は残存riskとして記録し、可能ならIAM Roles Anywhere等の一時資格情報へ移行する。ConsoleのIAM user「Security credentials」からaccess keyを一度だけ発行し、その場で各秘密ファイルへ直接記載する。期待結果は用途内操作成功、別bucket／別prefix／List全体／policy変更拒否、CloudTrail記録。

  5. lifecycle・CORS・削除

    未完了multipart、quarantine期限、noncurrent version、legal hold例外、browser PUT originを設定する。

    具体的な取得方法

    S3 Lifecycle公式文書に従い、未完了multipartは24時間、稼働系objectは削除要求から30日以内という上位要件と矛盾しないruleを作る。CORSは正規app originとPUTに限定する。期待結果は許可originの署名PUT成功、別origin拒否、期限試験で対象versionのみ削除、legal hold対象保持。

AWS資格情報の残存risk

管理者がファイルへ直接記載する方式では、host侵害時に長期access keyが取得され得る。最小権限、接続元制約、CloudTrail監視、定期rotation、旧key無効化確認を必須とし、未実施なら本番投入不可とする。

05 / External

外部サービスとapplication鍵

本番運用で必要になる外部資格情報と、application自身が生成する秘密を分離する。

  1. Stripe live keyとwebhook secret

    live secret key、webhook endpoint ID、endpoint signing secret、許可eventを取得する。

    具体的な取得方法

    Stripe Dashboardをlive modeに切り替え、API keys公式手順でrestricted keyを優先して作成する。webhook公式手順で本番HTTPS endpointを登録し、signing secretを取得する。期待結果はlive/test混在なし、署名済みevent成功、改変body／古いtimestamp拒否、raw bodyやsecretのlog出力0。

  2. 送信専用SMTP

    host、port、TLS mode、username、password、envelope-from、表示from、DKIM selectorを取得する。

    具体的な取得方法

    組織のmail管理者または利用providerの管理画面から送信専用accountを発行し、受信・管理権限を与えない。SPF、DKIM、DMARCをDNS一次情報と照合する。期待結果はTLS hostname検証成功、試験mail受信、SPF／DKIM pass、bounce経路確認、資格情報のlog出力0。

  3. WebAuthn RP IDとorigin

    RP ID、許可origin、表示名を公開DNSと一致させる。

    具体的な取得方法

    WebAuthn仕様に従い、RP IDは公開domain、originはscheme・host・portを含む正確なHTTPS originとする。wildcard、localhost、本番外originを含めない。期待結果は正規originで登録／認証成功、別subdomain／HTTP／別port拒否。

  4. application秘密鍵

    session HMAC、CSRF HMAC、field encryptionをそれぞれ独立した256bit以上の乱数として生成する。

    具体的な取得方法

    本番hostの作業directoryは/etc/stageaccord/secrets/application。対象fileごとに暗号学的乱数生成器を用い、値をterminal履歴や標準出力へ残さない管理手段で直接記載する。同じ値を使い回さない。期待結果は各fileのhashが相互に異なり、長さ要件を満たし、一般userが読めず、repository検索0件。

06 / Verification

起動前の完了判定

チェックが埋まったことではなく、拒否試験を含む実測結果で完了を判定する。

本番投入前の必須証拠
検証成功条件失敗時
設定schemaprofile集合一致、必須key欠落0、旧設定file 0、properties内の秘密値0service起動拒否

復旧交換host復元、旧秘密拒否、削除／失効再適用、再露出0、実測RPO／RTO記録本番投入不可

状態別確認

  • 設定直後: owner、mode、schema、hashを確認する。
  • service再起動後: 同じmodeとcredentialが読み込まれ、値はlogへ出ない。
  • 本番試験中: bypassは画面・監査・metricから識別でき、requiredへ自動復帰しない。
  • rollback後: 旧imageが新しい設定schemaを安全に読めない場合はrollbackを拒否する。
  • backup復元後: 失効済みsession、削除済みobject、旧access keyが復活しない。
結論

本書のチェックがすべて実測証拠へ結び付き、起動前検査が危険状態を拒否するまで本番投入不可。値を取得しただけ、設定fileを作っただけでは完了としない。
