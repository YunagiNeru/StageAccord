目的と設計境界

本書は、要件定義を実装可能なシステム境界、モジュール責務、データ保全、配置、運用、復旧へ落とし込む。詳細なクラス、全API項目、全テーブル定義は後続の詳細設計で確定する。

主な読者
開発者、インフラ運用者、セキュリティ・法務レビュー担当者、リリース判定者。
本書が決めること
実行時境界、依存方向、主要データ所有者、認証・認可境界、ファイル処理、非同期処理、単一ホスト配置、Amazon S3、監視、自動停止、復旧。
本書が決めないこと
画面ごとのピクセル仕様、全RESTスキーマ、全DDL、フレームワーク内部クラス、運用手順のコマンド列、法的助言の最終判断。
正本の責務
本書は「どう実現するか」の正本である。「何を満たすか」、優先度、状態、受入条件、事業・法務方針は要件定義書を正とする。
確定性
Production V1の設計判断と実装開始は承認済みである。数値、実機構成、既存基盤の実バージョンに関する未閉鎖事項はOPN-101〜103で管理し、所定の証拠なしに閉鎖しない。
優先順位
安全性 → 追跡可能性 → 可読性 → 移植性 → 採算性 → 実装速度。同順位なら、障害時に読み取り専用へ縮退できる案を採る。
単一の正本
業務状態と証跡はPostgreSQLを正本とする。オブジェクト本体はAmazon S3、短命セッションと短期キャッシュはValkeyに置く。削除・失効台帳と監査チェックポイントは主バックアップから独立して保全する。
変更規則
要件変更は要件書を先に改訂し、設計・実装・テストを追随させる。合意・承認・監査の履歴は上書き訂正せず、追加イベントで修正する。

公開面

インターネット公開はHTTPS 443のみ。HTTP 80はHTTPSへの転送に限定する。

管理面

VPN経由の分離ネットワークに限定し、SSH、DB、Valkey、ClamAV、監視、バックアップを公開しない。

ファイル

隔離領域から受入領域へ昇格し、ready、許可された検査状態、昇格receiptが一致するオブジェクトだけを配布する。

危険時

認可、検査、時刻、容量、複製、証明書、バックアップの異常時は対象操作を停止する。

本番投入判定

本書だけでは本番投入可としない。要件に定めた受入試験、復元訓練、脆弱性検査、法務・セキュリティ確認、実機・実UI確認、運用当番とロールバック確認がすべて通った場合に限り、リリース判定会議で可否を決める。

論理アーキテクチャ

Spring Bootのモジュラーモノリスを一つのデプロイ単位とし、業務境界ごとに内部モジュールを分離する。フロントエンドはReactとTypeScript、外部契約はRESTとOpenAPIで管理する。

web
React 19.2／TypeScript／Vite。公開画面、クリエイター画面、依頼者ポータル、運営画面をルートと権限で分離する。
Nginxから静的配信。APIとの通信は同一オリジンを基本とする。
application
JDK 25／Spring Boot 4.1。REST、認証・認可、業務トランザクション、Outbox書き込みを担う。
Production V1は単一ホスト・単一application processとする。サーバーセッションはValkeyに置く。
worker
同一コードベースの別プロセス。通知、ファイル検査、プレビュー、監査連携、再試行をOutboxからat-least-onceで実行する。
集約内連番、60秒リース、送信先冪等キー、指数バックオフ、10回または24時間で隔離キュー、理由付き手動再送を持つ。
postgres
PostgreSQL 18。業務状態、版、承認、監査、Outbox、冪等性記録の正本。
主系は同期的にローカル永続化し、待機系へWAL転送する。
valkey
サーバーセッション、レート制限、短期キャッシュ、短命ロック。
消失しても業務正本を失わない。復旧後は全セッションを再発行する。
amazon-s3
隔離、受入済み、プレビュー、配信を別バケットに分離する外部オブジェクトストレージ。
公開アクセス遮断、デフォルト暗号化、バージョニング、用途別IAM権限を必須とし、リージョンとバケット名を外部設定にする。受入用cleanバケット名と検査状態は分離する。
clamav
オンプレミス専用ホストへTCPで接続し、requiredではINSTREAMでアップロード本文を検査する。bypassでは接続しない。
TCP socket自体に暗号化・認証がないため信頼済みネットワークと送信元制限を必須とする。結果はcleanとbypassedを区別する。

中核フローと整合性

同期トランザクションは状態変更とOutbox記録までを一単位とし、外部送信と重い処理はワーカーへ渡す。再試行しても二重通知、二重承認、二重請求を発生させない。

  1. 受付から条件提示

    公開中のサービス版を依頼へ固定し、フォーム回答を保存する。審査で承認した時点では案件を開始せず、条件提示版と承認者規則を生成する。

  2. 合意成立

    対象版、当事者、認証時刻、表示ハッシュを再確認し、各当事者の明示操作を追記する。必要人数が揃った時だけ合意成立イベントを発行する。

  3. 案件生成と進行

    合意版から案件フローを複製し、後のテンプレート変更から隔離する。チェックポイントは順序、入力、提出物、承認条件を満たした場合だけ遷移する。

  4. 修正と変更注文

    仕様内修正、仕様不一致の訂正、追加変更を別のコマンドとして扱う。追加変更は変更注文の再合意前に作業対象へ入れない。

  5. 最終納品と受領

    運用モードに従って受入済みとなったcleanまたはbypassedファイルだけから納品パッケージを固定し、受領対象版を再表示する。受領は自動成立させず、明示操作と監査記録を残す。

ファイル取込パイプライン

公開権限
開始・署名・完了・中止・再開はアプリのアップロード制御APIだけが受け付ける。ブラウザにはAmazon S3 quarantineの単一パートPUT権限だけを発行する。
ListBucket、DeleteObject、CompleteMultipartUpload、管理API、clean／previewバケット、他案件キーを公開しない。
checksum
CreateMultipartUploadでSHA256を指定し、各UploadPartの署名対象にx-amz-checksum-sha256を含める。アプリはpart checksumとETagを記録し、同じ一覧で完了する。
workerが完成オブジェクト全体を読み、実サイズと全体SHA-256を算出してDBへ保存する。ETagを内容ハッシュとして扱わない。
上限
1ファイル4,000,000,000バイト、64MiBパート、最大60パート、署名15分、multipart全体24時間。
最終パートだけ64MiB未満を許可する。上限超過は開始前に拒否し、外部URL共有へ案内する。
検査領域
workerごとに12GiBの暗号化一時領域を割り当て、同時検査1件、CPU 2コア、メモリ8GiB、30分で打ち切る。
非root、ネットワークなし、read-only root、cap_drop ALL、no-new-privileges、seccomp/AppArmorを強制する。
ClamAV
専用ホストのClamAV 1.5系列へTCP接続し、required時だけINSTREAMで本文を送る。StreamMaxLengthを4,000,000,000バイト以上とし、アプリ側も4GB上限を強制する。
実サイズと送信済みバイト数が一致しない場合、上限超過、タイムアウト、ERRORはscan_errorとする。bypassはbypassedとし陽性・陰性を記録しない。
昇格
requiredでは陰性結果、定義版、設定ハッシュを、bypassではバイパス理由と設定版を記録する。両モードでSHA-256、bucket、key、version ID、サイズをDBへ保存し、受入用のcleanバケットへコピーする。
cleanは互換性のため維持するバケット名であり検査結果ではない。コピー後の照合と昇格receiptが揃った場合だけ、検査状態を保持したままreadyへ遷移する。
回収
未完了multipartは24時間、陽性とscan_errorの隔離実体は7日で削除する。
法的保持がある場合だけ削除を停止し、保持判断を削除・失効台帳へ記録する。

Transactional Outbox

業務更新とOutboxイベントを同じPostgreSQLトランザクションに書く。ワーカーはevent_idと送信先を冪等キーにし、aggregate_sequence順に60秒リースで処理する。失敗は1分、5分、30分、2時間、12時間の後に再試行し、10回または24時間で隔離する。手動再送は原因、操作者、対象範囲を監査し、暗黙に破棄しない。

時刻劣化と監査継続

  1. 異常を検知

    NTP offsetが2秒を超えたホストをtime_trust=degradedへ遷移し、合意、承認、受領を拒否する。

  2. 拒否を記録

    検知、拒否、管理操作、復旧試行をsequence、単調時刻、観測wall clock、offset、ホストIDとともに監査へ追記する。

  3. DB停止時も保全

    暗号化専用ボリュームのappend-only spoolへホスト署名付きで追記し、上限80％で管理操作も停止する。上書き循環はしない。

  4. 回復後に統合

    複数NTP源で10分連続して1秒以内となり、二者確認後に信頼状態を戻す。spoolはホスト連鎖と元時刻を保ったままDBへ取り込む。

削除・失効台帳

削除、非公開化、アクセス失効、法的保持は、主バックアップの復元対象から独立した署名付きappend-only台帳へ書く。台帳はアクセス制御された暗号化バックアップへ保全する。古い復旧点の公開前に、台帳をDB、検索射影、Valkey、Amazon S3、通知キューへ再適用し、対象件数とハッシュが一致しなければ公開しない。

認可評価の順序

  1. 主体を確定

    セッション、MFA、再認証時刻、失効世代、運営者の支援権限を検査する。

  2. テナントと関係を確定

    ワークスペース所属、案件参加、依頼者メール、対象ファイル・コメント・承認との所有関係を検査する。

  3. 操作と属性を評価

    役割、案件状態、公開範囲、対象版、期限、緊急停止、縮退状態を同時に評価する。

  4. 結果を記録

    重要操作の許可は監査へ追記し、拒否は秘密を含まない理由コードと相関IDを残す。評価不能は拒否する。

支援アクセスと緊急停止

通常の運営者権限では案件本文を閲覧できない。支援アクセスは利用者または通報案件に結び付くチケット、対象案件、目的、許可操作、60分以内の期限を申請し、申請者と異なる承認者が再認証して発行する。内容は既定でマスクし、閲覧・検索・出力を利用者向け監査へ記録する。緊急停止は開始者と別担当者の確認を必要とし、解除条件の充足、再認証、二者承認がなければ解除できない。

公開後の残存経路

公開情報を後から非公開にしても、アクセスログ、監査ログ、バックアップ、メール通知、受領済みファイル、第三者のスクリーンショットには残り得る。公開前の許可項目検査を主防御とし、削除処理は現行DBだけでなく、キャッシュ無効化、検索射影、期限到来後のバックアップ失効、復元後の削除再適用まで含める。

Stripe照合と利用権

Webhookは署名、許容時刻窓、event ID一意制約、subscription単位の集約内連番で保存し、at-least-onceで処理する。逆順イベントは取得したStripe最新状態と比較し、古い状態へ戻さない。毎日02:00 JSTに全契約をStripe APIからページング取得し、契約・請求・利用権を照合する。不一致、API停止、署名失敗中は有料利用権を新たに拡大せず、既存利用者は要件の7日猶予または読取り専用へ遷移する。

リリース経路

  1. ビルドと供給網検査

    固定依存、SBOM、ライセンス、静的解析、テスト、秘密検査、コンテナ脆弱性検査を実行し、成果物へ署名する。

  2. 前方互換マイグレーション

    expandを先行し、現行N版と直前N-1版が同じDBへ接続できることを検証する。バックアップと復元検証が期限内でなければ実行しない。

  3. 保守停止とN版反映

    単一ホストへの外部トラフィックを保守表示へ閉じ、digest固定N版を反映する。N-1版はDB contractまで署名済みdigestと設定互換性を検証した状態で保持する。

  4. 閉域検証と公開

    外部トラフィックを閉じたまま起動前検査、合成試験、エラー率、p95、Outbox、DB負荷、Amazon S3、容量を確認する。全項目が合格した場合だけ公開し、不合格ならN-1へ戻すか前進修復する。

  5. 契約整理

    backfill完了、二回の本番リリース成功、14日経過、旧版トラフィックゼロを確認した後だけcontractを実行する。以後はDB逆変換をせず前進修復する。

追跡の読み方

各行の主制御は実装の入口であり、要件をその制御だけへ閉じ込める意味ではない。試験IDはリリース証拠の必須識別子であり、試験実施済みを表すものではない。要求判断は全106件で追跡し、数値・実機・基盤・検証基盤の未閉鎖事項はOPN IDで参照する。

追跡の機械検証

OPN-104で実装したCIは、要件定義書、HLD、LLDから要件IDを抽出し、集合差分が空であること、一要件につき追跡行が一つであることを確認する。欠落、未知ID、重複ID、リンク切れ、空欄が一件でもあればドキュメント検証を失敗させる。
