目的と設計境界

本書は、要件定義を実装可能なシステム境界、モジュール責務、データ保全、配置、運用、復旧へ落とし込む。詳細なクラス、全API項目、全テーブル定義は後続の詳細設計で確定する。

主な読者
開発者、インフラ運用者、セキュリティ・法務レビュー担当者、リリース判定者。
本書が決めること
実行時境界、依存方向、主要データ所有者、認証・認可境界、ファイル処理、非同期処理、二拠点配置、監視、自動停止、復旧、クラウド移行判定。
本書が決めないこと
画面ごとのピクセル仕様、全RESTスキーマ、全DDL、フレームワーク内部クラス、運用手順のコマンド列、法的助言の最終判断。
正本の責務
本書は「どう実現するか」の正本である。「何を満たすか」、優先度、状態、受入条件、事業・法務方針は要件定義書を正とする。
確定性
Production V1の概要設計に未確定事項はない。詳細設計、専門確認、試験、訓練は本書の判断を変更する未決事項ではなく、リリース前に証拠を提出する実行条件である。
優先順位
安全性 → 追跡可能性 → 可読性 → 移植性 → 採算性 → 実装速度。同順位なら、障害時に読み取り専用へ縮退できる案を採る。
単一の正本
業務状態と証跡はPostgreSQLを正本とする。オブジェクト本体はCeph RGW、短命セッションと短期キャッシュはValkeyに置く。削除・失効台帳と監査チェックポイントは主バックアップから独立して保全する。
変更規則
要件変更は要件書を先に改訂し、設計・実装・テストを追随させる。合意・承認・監査の履歴は上書き訂正せず、追加イベントで修正する。

公開面

インターネット公開はHTTPS 443のみ。HTTP 80はHTTPSへの転送に限定する。

管理面

VPN経由の分離ネットワークに限定し、SSH、DB、Ceph管理面、監視、バックアップを公開しない。

ファイル

隔離領域から検査済み領域へ昇格したオブジェクトだけを配布する。

危険時

認可、検査、時刻、容量、複製、証明書、バックアップの異常時は対象操作を停止する。

本番投入判定

本書だけでは本番投入可としない。要件に定めた受入試験、復元訓練、脆弱性検査、法務・セキュリティ確認、実機・実UI確認、運用当番とロールバック確認がすべて通った場合に限り、リリース判定会議で可否を決める。

中核フローと整合性

同期トランザクションは状態変更とOutbox記録までを一単位とし、外部送信と重い処理はワーカーへ渡す。再試行しても二重通知、二重承認、二重請求を発生させない。

  1. 受付から条件提示

    公開中のサービス版を依頼へ固定し、フォーム回答を保存する。審査で承認した時点では案件を開始せず、条件提示版と承認者規則を生成する。

  2. 合意成立

    対象版、当事者、認証時刻、表示ハッシュを再確認し、各当事者の明示操作を追記する。必要人数が揃った時だけ合意成立イベントを発行する。

  3. 案件生成と進行

    合意版から案件フローを複製し、後のテンプレート変更から隔離する。チェックポイントは順序、入力、提出物、承認条件を満たした場合だけ遷移する。

  4. 修正と変更注文

    仕様内修正、仕様不一致の訂正、追加変更を別のコマンドとして扱う。追加変更は変更注文の再合意前に作業対象へ入れない。

  5. 最終納品と受領

    検査済みファイルだけから納品パッケージを固定し、受領対象版を再表示する。受領は自動成立させず、明示操作と監査記録を残す。

業務更新とOutboxイベントを同じPostgreSQLトランザクションに書く。ワーカーはevent_idと送信先を冪等キーにし、aggregate_sequence順に60秒リースで処理する。失敗は1分、5分、30分、2時間、12時間の後に再試行し、10回または24時間で隔離する。手動再送は原因、操作者、対象範囲を監査し、暗黙に破棄しない。

復旧後は全セッションを再発行し、PostgreSQLの認可世代から安全に再同期する。権限を拡大するフォールバックは禁止。

コード、イメージ、一般設定から分離し、SOPS暗号化設定をTPM封印済みホスト鍵で復号してsecret mountへ注入する。

時刻劣化と監査継続

  1. 異常を検知

    NTP offsetが2秒を超えたホストをtime_trust=degradedへ遷移し、合意、承認、受領を拒否する。

  2. 拒否を記録

    検知、拒否、管理操作、復旧試行をsequence、単調時刻、観測wall clock、offset、ホストIDとともに監査へ追記する。

  3. DB停止時も保全

    暗号化専用ボリュームのappend-only spoolへホスト署名付きで追記し、上限80％で管理操作も停止する。上書き循環はしない。

  4. 回復後に統合

    複数NTP源で10分連続して1秒以内となり、二者確認後に信頼状態を戻す。spoolはホスト連鎖と元時刻を保ったままDBへ取り込む。

削除・失効台帳

削除、非公開化、アクセス失効、法的保持は、主バックアップの復元対象から独立した署名付きappend-only台帳へ書く。台帳は主・副・第三保管場所へ一方向複製し、毎日オフライン媒体へ固定する。古い復旧点の公開前に、台帳をDB、検索射影、Valkey、Ceph、通知キューへ再適用し、対象件数とハッシュが一致しなければ公開しない。

認可評価の順序

  1. 主体を確定

    セッション、MFA、再認証時刻、失効世代、運営者の支援権限を検査する。

  2. テナントと関係を確定

    ワークスペース所属、案件参加、依頼者メール、対象ファイル・コメント・承認との所有関係を検査する。

  3. 操作と属性を評価

    役割、案件状態、公開範囲、対象版、期限、緊急停止、縮退状態を同時に評価する。

  4. 結果を記録

    重要操作の許可は監査へ追記し、拒否は秘密を含まない理由コードと相関IDを残す。評価不能は拒否する。

支援アクセスと緊急停止

通常の運営者権限では案件本文を閲覧できない。支援アクセスは利用者または通報案件に結び付くチケット、対象案件、目的、許可操作、60分以内の期限を申請し、申請者と異なる承認者が再認証して発行する。内容は既定でマスクし、閲覧・検索・出力を利用者向け監査へ記録する。緊急停止は開始者と別担当者の確認を必要とし、解除条件の充足、再認証、二者承認がなければ解除できない。

公開後の残存経路

公開情報を後から非公開にしても、アクセスログ、監査ログ、バックアップ、メール通知、受領済みファイル、第三者のスクリーンショットには残り得る。公開前の許可項目検査を主防御とし、削除処理は現行DBだけでなく、キャッシュ無効化、検索射影、期限到来後のバックアップ失効、復元後の削除再適用まで含める。

バックアップ・復旧・再露出防止

RPO 15分、RTO 4時間を設計目標とし、バックアップが存在することではなく、隔離環境で復元し業務整合性を検証できることを合格条件とする。

  1. 障害を宣言し書込みを止める

    監視担当とインシデント指揮者が宣言し、公開入口を保守表示へ切り替える。監査は劣化モードで継続する。

  2. 旧主系を隔離する

    旧主系のPDU電源断を確認し、ファイアウォールから公開VIP、拠点間VPN、管理経路を削除する。いずれかを確認できなければ昇格しない。

  3. 排他世代を取得する

    主・副・第三地点の3ノードetcdで、副拠点と第三地点の多数派から単回昇格リースを取得する。二名が世代番号とフェンス証拠へ署名する。

  4. 復旧点を確定する

    5分ごとの復旧マニフェストから、15分以内のDB LSNとRGW複製watermarkを選ぶ。全DB参照のbucket、key、version ID、サイズ、SHA-256、scan resultを副ゾーンで照合する。

  5. データ層を昇格する

    PostgreSQL待機系を昇格し、Ceph RGWの副zoneをmaster・read-only=falseへ変更してperiodをcommitする。アプリは新しい昇格世代を持つ接続だけを受け付ける。

  6. 削除と認証を安全化する

    独立台帳から削除・非公開化・失効・法的保持を再適用し、全セッション、ワンタイムリンク、管理者昇格、復旧コード、短命URL、影響した秘密の世代を更新する。

  7. 限定公開から通常公開へ進む

    DNS/VIPを副拠点へ切り替え、運用者だけの読取り、代表書込み、監査、Outbox、ファイル配布、複製、バックアップを確認した後に段階的に利用者トラフィックを戻す。

  8. 旧主系を再構築する

    旧環境をそのまま再参加させず、ディスク初期化、鍵再発行、現主系からのフル再同期、フェンス解除、再検証を行う。旧主系への逆昇格は別の切替訓練として扱う。

ロールバックの原則

アプリは一つ前の署名済みイメージへ戻せるが、DBマイグレーションは破壊的な逆変換を前提にしない。旧版が新旧両形式を読める期間を確保し、データ変換後は前進修復を優先する。ロールバック先が危険な設定、失効前の秘密、非対応スキーマを含む場合は自動的に拒否する。

Stripe照合と利用権

Webhookは署名、許容時刻窓、event ID一意制約、subscription単位の集約内連番で保存し、at-least-onceで処理する。逆順イベントは取得したStripe最新状態と比較し、古い状態へ戻さない。毎日02:00 JSTに全契約をStripe APIからページング取得し、契約・請求・利用権を照合する。不一致、API停止、署名失敗中は有料利用権を新たに拡大せず、既存利用者は要件の7日猶予または読取り専用へ遷移する。

リリース経路

  1. ビルドと供給網検査

    固定依存、SBOM、ライセンス、静的解析、テスト、秘密検査、コンテナ脆弱性検査を実行し、成果物へ署名する。

  2. 前方互換マイグレーション

    expandを先行し、現行N版と直前N-1版が同じDBへ接続できることを検証する。バックアップと復元検証が期限内でなければ実行しない。

  3. 限定反映

    一部インスタンスへ反映し、起動前検査、合成試験、エラー率、p95、Outbox、DB負荷を確認する。

  4. 全体反映

    段階的に切り替え、旧版を即時退避できる状態で維持する。フェイルクローズ条件に触れた場合は自動停止する。

  5. 契約整理

    backfill完了、二回の本番リリース成功、14日経過、旧版トラフィックゼロを確認した後だけcontractを実行する。以後はDB逆変換をせず前進修復する。

追跡の読み方

各行の主制御は実装の入口であり、要件をその制御だけへ閉じ込める意味ではない。試験IDはリリース証拠の必須識別子であり、試験実施済みを表すものではない。未確定欄は全107件で「なし」である。

追跡の機械検証

CIでは要件定義書と本書から要件IDを抽出し、集合差分が空であること、一要件につき追跡行が一つであることを確認する。欠落、未知ID、重複ID、リンク切れ、空欄が一件でもあればドキュメント検証を失敗させる。

残余リスクと検知

オンプレ運用能力
少人数運用では回線、電源、証明書、バックアップ、パッチ、当番の集中が単一障害点になり得る。
当番不在、期限超過、訓練未実施を監視し、代行可能なRunbookと四半期訓練を持つ。
4GBファイル
長時間転送、再送、完全検査、複製待ち、プレビュー生成が容量とキューを圧迫する。
分割完了率、検査p95、実読込量、複製遅延、滞留、隔離容量、回線エグレスを計測する。
外部依存
メール、Stripe、DNS、NTPの障害は認証、請求、公開、証跡時刻へ影響する。
タイムアウト、サーキットブレーカー、署名検証、Outbox再試行、時刻フェイルクローズを使う。
法的適合
取引条件、個人情報、年齢、権利条件は実装だけで最終適合を保証できない。
公開前と重要変更時に専門家の文書確認を必須ゲートにする。
復旧実効性
RPO／RTOは設計値であり、訓練しなければ実績ではない。
復元・切替の所要時間、欠損、手作業、再露出を記録し、目標超過を改善案件にする。
