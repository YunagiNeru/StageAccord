本書はLLDの代替設計ではなく、LLDを承認可能な状態へ修正するためのレビュー正本である。

03 / Strengths

成立している点

以下は維持すべき設計資産であり、修正時に削除または弱体化してはならない。

  • REQUIREMENTSのFR 83件・NFR 24件、計107件はHLD追跡表に重複・欠落なく存在する。
  • HLDの安定ID 30件はLLD追跡表に重複・欠落なく存在する。
  • 三文書に重複IDと文書内リンク切れは見つからなかった。
  • モジュラーモノリス、内向き依存、schema所有権、Transactional Outbox、既定拒否の方向性は一貫している。
  • ファイルの隔離・全本文検査・副拠点照合、時刻劣化、二重fence、復元後の認証失効、削除再適用を設計対象に含めている。
  • 正常系だけでなく、重複、逆順、期限、依存停止、復元後を試験観点へ含めている。

04 / Blocker

実装を止める指摘

一件でも未解決なら、API、DB、認証、ファイル、復旧の後戻りが大きいため実装開始を承認しない。

根拠となる観測

REQ-304

HTTP DELETEと冪等性の適用範囲を分離する

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
HTTP共通契約／認証・メンバー・アップロード・削除API
参照
LLD HTTP共通契約 LLD endpoint台帳

非同期データ削除、セッション失効、メンバー失効、multipart中止を同一のDELETE契約で扱わず、各操作の応答、冪等性、再試行、監査、秘密応答の保存可否を個別に定義しなければならない。

影響

実装ごとに200、202、204が分岐し、単回tokenやsession応答が再配布される。クライアント再試行が失効操作や秘密発行を誤って再現する。

必須修正

HTTP操作を「即時失効」「冪等な中止」「非同期削除」「秘密発行」「一般command」に分類し、status code、応答body、Idempotency-Key要否、保存可能フィールド、保持期間を表で定義する。

解消条件

全endpointが一つの操作分類へ所属し、認証token、Cookie、署名URL、復旧情報をidempotency responseへ保存・再返却しない試験がある。

根拠となる観測

共通契約はDELETEを202とdeletionRequestIdを返す削除workflowと規定するが、endpoint台帳には logout、membership revoke、upload abort、file deletionが同じDELETEで存在する。また全POST commandへIdempotency-Keyを要求し、response bodyを保存する設計は、login、再認証、link redemption、download grantなど秘密を返す操作にも適用され得る。

種別
要求

必須
適用範囲

参照
LLD 認証・公開境界 LLD ファイル HLD-NET-001 NFR-SEC-002

REQ-311

LLD 削除再適用 HLD-DEL-001 NFR-PRV-002 NFR-BCP-001

削除・失効台帳の保存形式、署名、順序、冪等性、複製、利用不能時の停止範囲を定義し、Object Lockのbucket、mode、retention期間が30日削除要件と競合しないことを証明しなければならない。

影響

削除済み情報が復元・再公開される、またはWORM保持により約束した期限内に削除できない。台帳停止時に通常書込みだけ継続し、後で削除不能になる。

必須修正

台帳append契約と復元適用状態機械を追加し、各bucketのversioning、Object Lock mode、retention、legal hold、delete marker、backup期限を表にする。台帳へappendできない操作は確定しない。

解消条件

削除前backup復元、Object Lock有無、legal hold、台帳停止、重複append、複製遅延の試験で、公開再露出ゼロと期限説明が成立する。

根拠となる観測

LLDはDELETION_LEDGER_ENDPOINTと復元時再適用を定めるが、台帳のAPI・schema・event ID・ack・再試行・terminal hash生成を定義しない。Ceph bucketへObject Lockを要求する一方、稼働DB・オブジェクトを削除要求から30日以内に削除する要件との優先関係がない。

07 / Sequence

修正順序

下流のAPIやDDLを先に確定すると再作業になるため、境界から詳細へ進める。

  1. 外部境界を固定する

    REQ-301、REQ-302、REQ-308、REQ-309、REQ-310を解消し、画面・API・origin・配布方式を決める。

  2. 業務と認可を固定する

    REQ-303、REQ-304、REQ-305、REQ-307を解消し、状態、HTTP、役割、認証を一意にする。

  3. 永続化と信頼基盤を固定する

    REQ-306、REQ-311、REQ-312、REQ-313、REQ-314、REQ-315を反映する。

  4. 運用機能と互換性を閉じる

    REQ-316、REQ-317、REQ-319を反映し、障害・通知・rolling deploymentを試験可能にする。

  5. 追跡と文書状態を更新する

    REQ-318、REQ-320、Minorを反映し、全recordを再審査する。
