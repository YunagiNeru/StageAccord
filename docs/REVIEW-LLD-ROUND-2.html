01 / Contract

文書契約

本書は修正済みLLDの実装開始可否を判断するレビュー正本である。上位文書の要求を変更せず、LLDの解消状況と残存問題だけを扱う。

対象範囲
API、Web、状態、データ、認証、ファイル、監査、削除、DR、追跡、文書品質
対象外
ソースコード品質、実環境性能、実機配線、法的文言の適法性、第三者製品の実挙動
優先関係
REQUIREMENTS → HLD → LLD → 本レビュー。競合時はLLDを修正する
レビュー方法

前回22件の解消条件を一件ずつ照合し、107要求の集合、HLDリンク、endpoint、operationId、状態、DB role、暗号、権限、削除、復旧の内部整合を機械・目視で確認した。実装証拠がないため、「設計上成立」と「実装済み」を区別する。

04 / Accepted improvements

改善された点

以下は今回の再レビューで設計改善として確認できた。残存Blockerを理由に、これらを巻き戻す必要はない。

  • Web route、server state、局所state、Problem Details、upload、WCAG試験の責務が一章に集約された。
  • app、upload、preview、filesのoriginが分離され、session Cookieを未信頼contentへ送らない方針になった。
  • Valkey障害を401やlocal rate fallbackへ変換せず、入口別に503でfail closeする契約が追加された。
  • 通知のrecipient、template、dedupe、channel、既読、必須通知が状態機械と保存表へ接続された。
  • 107要求の直接追跡が完全化され、上位文書リンクと内部リンクの欠落は検出されなかった。
  • N／N-1互換、物理node、network allowlist、具体的な露出連鎖が追加された。
  • 文書状態が「再レビュー待ち・実装開始不可」とされ、未承認recordを承認済みと偽っていない。

05 / Findings

残存・新規指摘

Blockerは実装開始を停止する。Majorは局所修正に見えても公開契約・安全性へ影響するため、実装前に全件閉じる。

REQ-321

公開API台帳を実装可能な単一契約へ完成させる

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
HTTP／OpenAPI／Web route／要件追跡
関連
REQ-302、REQ-304、FR-REQ-004

Production V1の公開HTTP面は、全routeと利用者操作についてmethod、path、operationId、operation class、許可主体、成功status、主要error、冪等性、競合条件を一件一行で確定し、OpenAPI生成前に集合差分を0にしなければならない。

根拠となる観測

  • 文書には97件のendpoint行があるが、操作分類を明記しているのは補完APIの38件であり、主台帳59件は分類が未記載である。
  • `ListRequests`はmodule公開契約とFR-REQ-004の追跡開始点に存在するが、対応するGET endpointがない。
  • Web routeが要求するcreator側のrequest一覧、service／workflow一覧・取得、creator project詳細などのquery契約が公開API台帳に揃っていない。
  • 主台帳は成功statusと主要error codeを列として持たず、「Production V1の公開HTTP面」という自己宣言を満たしていない。

影響

OpenAPI、生成client、route loader、認可試験、冪等性middlewareが同じ契約から実装できず、実装者ごとにstatus codeと再試行条件が分岐する。

必須修正

全endpoint台帳を一つに統合し、`x-operation-class`を文書上にも表示する。Web route registry、module use case、107件追跡、OpenAPI operationIdの集合差分をCI対象にする。

解消条件

全外部route／操作が一意なoperationへ到達し、未分類0、重複0、開始点欠落0、成功status・主要error空欄0となること。

REQ-322

認証要素・password reset・recovery codeのlifecycleを安全に確定する

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
identityaccess／認証API／Account recovery
関連
REQ-307、FR-ACC-004、FR-ACC-005

メール単体でcredentialを変更できる経路を設けず、Passkey、TOTP、recovery codeの追加、確認、削除、再生成、最後の強要素保護、全体失効をAPI・状態・保存・通知・監査まで一意に定義しなければならない。

根拠となる観測

  • `CompletePasswordReset`は匿名のchallenge所持者だけを主体とし、既存Passkey、TOTP、recovery code、72時間手動審査のいずれも要求していない。
  • `ConfirmMfaEnrollment`はHTTP 204としながら「回復codeを一度だけ発行」と記載し、bodyを持てないresponse契約と矛盾する。
  • 追加Passkey、Passkey削除、TOTP削除、recovery code再生成のendpointと状態がない。
  • 「active要素ゼロへの通常削除禁止」はDB辞書にあるが、どの要素を最後の強要素として数えるか、要素変更時の全session失効が公開契約にない。

影響

メール侵害からpassword変更またはaccount lockoutが可能になり、回復codeを利用者へ安全に渡せず、端末紛失時の運用が実装者判断になる。

必須修正

password resetを強要素確認またはRecoveryCaseへ統合する。MFA確認responseを200／201のSECRET_ISSUEとして一回だけ返すか、別のrecovery-code issuance endpointへ分離する。要素一覧・追加・削除・再生成APIを追加する。

解消条件

メールだけではcredential変更・session成立ができず、全要素lifecycle、最後の要素保護、再認証、世代失効、通知、監査のE2Eが定義されること。

REQ-323

ファイル配布方式とFile／Preview状態を一つに統一する

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
filehandling／download gateway／状態機械／origin
関連
REQ-303、REQ-309、FR-FIL-001、FR-FIL-005

ファイル取得はgateway方式または直接署名URL方式のどちらか一つに固定し、grant secretの輸送、GET／HEAD／Range、期限、単回性、再認可、失効、Cache-Control、ログ秘匿、およびFileVersionとPreviewAssetの状態を同じ契約から実装できなければならない。

根拠となる観測

  • DEC-209とFILE-CONTROLは「browserへRGW署名URLを渡さずgatewayがstream」と定義する一方、取込手順のDistributeは「5分以内の署名URLを返す」と記載する。
  • `files.example`で実行する実際のGET／HEAD path、grant tokenをheader・body・fragment・URLのどこで渡すか、Range再利用と単回性の関係がない。
  • TERM-CATALOGとIssueDownloadGrantは`download_only`をFile状態のように扱うが、STATE-PREVIEWはPreview capabilityとして扱う。
  • STATE-FILEは`infected`を終端と記載しつつ、同じ表で`* → deletion_pending → deleted`を許可している。

影響

失効後も取得できる実装、secretのURL・履歴・Referer漏えい、APIとDBで異なるstate enum、悪性ファイルを削除できない状態が発生する。

必須修正

gatewayの公開interfaceを別表で定義し、grant token輸送とRange契約を固定する。FileVersionの安全状態とPreviewAssetの能力を別enumにし、`download_only`をcapabilityへ統一する。infected／scan_errorの削除遷移を明示する。

解消条件

配布方式の言い換えが全章で一致し、File／Preview状態集合差0、失効後GET 0件、secretのURL・log・history残存0件となること。

REQ-324

削除要求・独立台帳・Object Lockを原子的かつ期限内に成立させる

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
DeletionRequest／独立台帳／Ceph／backup
関連
REQ-312、NFR-PRV-002、HLD-DEL-001

削除要求の正本、独立台帳entry、ack、冪等キー、署名chain、複製、再試行、terminal receiptを定義し、Object Lock対象を30日・35日の削除期限と競合しない情報だけに限定しなければならない。

根拠となる観測

  • STATE-DELETIONは外部台帳append成功前に202を返さないとするが、DB transactionと独立endpointの間の二重書込みを整合させるprotocolがない。
  • `DELETION_LEDGER_ENDPOINT`とprojectionはあるが、独立台帳のentry schema、sequence、idempotency、ack、署名、timeout後の判定がない。
  • DeletionRequestの状態機械とAPIはあるが、workflow正本となる所有tableがDDL manifestにない。
  • DEC-212は利用者fileに固定WORMを設定しない一方、FILE-CONTROLは「契約上の凍結成果物」をcompliance bucketへ複製するとし、削除要求から30日以内のlive object削除と競合する。

影響

台帳だけ成功／DBだけ成功の孤児状態、削除完了の誤通知、削除期限超過、復元後の再露出が起きる。

必須修正

DeletionRequest所有module・tableを追加し、DB Outbox→独立ledgerの冪等append→ack→projectionのsagaを定義する。compliance bucket対象から利用者成果物を除くか、上位要件で法的保持対象と期限を明示的に変更する。

解消条件

通信切断の全位置で再実行してもentry一件、202後の追跡可能性100％、通常fileの30日削除、backup35日失効、復元後再露出0件となること。

REQ-325

監査eventをappend function以外から書けないようにする

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
audit schema／DB role／hash chain
関連
REQ-311、FR-AUD-002

audit_eventへの書込みはchain headをロックする単一のSECURITY DEFINER functionだけに限定し、application、worker、運用roleへtable直接INSERT・UPDATE・DELETE権限を与えてはならない。

根拠となる観測

  • 監査手順とDB-ROLE表は`audit_append` function経由・直接INSERT拒否を定義する。
  • 一方、主要テーブル辞書の`audit.audit_event`は「app roleはINSERT/SELECTのみ」と記載し、functionを迂回する直接INSERTを許可している。
  • 直接INSERTではglobal sequence、previous_hash、event_hash、chain head lockを強制できない。

影響

悪意または実装ミスでchainに接続しない監査eventを挿入でき、改変検知と日次署名の意味が崩れる。

必須修正

辞書をfunction-onlyへ修正し、base table権限を全runtime roleからREVOKEする。functionの固定search_path、所有者、入力上限、canonicalization、transaction rollbackを定義する。

解消条件

runtime roleによる直接INSERT／UPDATE／DELETEが全て拒否され、並行function appendだけが連続chainを生成すること。

REQ-326

promotion generationをDBとRGWのserver側強制へ落とす

Blocker 未確定
種別
要求
規範強度
必須
適用範囲
DR／PostgreSQL／RGW／worker
関連
REQ-313、NFR-BCP-002、HLD-DR-001

旧site・旧generationのprocessがapplication codeを迂回しても書けないよう、site別DB role、全transactionのserver-side generation gate、既存session切断、site別RGW credential失効、worker fencing tokenを具体的に定義しなければならない。

根拠となる観測

  • DEC-213は全transactionとobject writeへ世代を要求すると述べるが、DB-ROLEにはsite／generation別roleがなく、設定も単一`DB_USERNAME_FILE`である。
  • 行UPDATEへgeneration条件を加えるだけでは新規INSERT、sequence採番、監査function、DDL外の副作用を止められない。
  • `NOLOGIN`やGRANT取消だけでは既存connection poolを確実に終了する手順がなく、`pg_terminate_backend`相当の扱いがない。
  • RGW credentialの世代、発行、旧key削除確認、失効不能時の昇格停止が構成台帳にない。

影響

network fenceの一部失敗や旧process生存時にsplit-brain書込みが成立し、RPO、監査順序、削除台帳、object versionが破壊される。

必須修正

site-generationごとのDB login roleとRGW access keyを発行し、昇格transactionで旧role権限取消・NOLOGIN・session終了を確認する。DB guard table＋transaction設定／trigger／functionで全writeを検査し、worker leaseにもgenerationを含める。

解消条件

旧site生存、旧connection、旧worker、旧S3 keyを使った全write試験で確定副作用0件となり、失効確認不能時は昇格しないこと。

REQ-327

DDL辞書を実際にmigrationへ変換できる完全性へ上げる

Blocker 未確定
種別
要求
規範強度
必須
適用範囲

関連
REQ-314、REQ-315

全table・columnについてSQL型、NULL、default、PK、FK、unique、CHECK、index、immutable、暗号envelope、保持classを明示し、抽象参照やID配列でtenant境界を迂回してはならない。

根拠となる観測

実装者ごとにNULLと型、cascade、参照整合性が変わり、workspace越境、状態不能、migration非互換が生じる。

解消条件

Flyway migrationが推測なしに生成可能で、nullable集合差0、FK未定義0、tenant FK欠落0、全state正本table存在となること。

06 / Failure chain

露出・障害連鎖

残存問題が本番へ入った場合の多段階悪化経路を示す。単発のAPI不備ではなく、削除、復旧、公開、第三者保存まで連鎖する。

  1. download grantの輸送が曖昧なまま実装される

    実装者がquery付きURLまたは直接RGW URLを採用し、browser履歴、Referer、access logへsecretが残る。

  2. 権限失効後も取得される

    client roleやproject grantを失効しても、発行済みURLまたはcacheから成果物を取得できる。

  3. 第三者へ保存・転載される

    取得者、画面共有、ブラウザ同期、スクリーンショット保持者がファイルやURLを外部へ複製する。

  4. 削除要求後もcompliance objectが残る

    凍結成果物のObject Lockと30日削除が競合し、削除完了表示と実体が一致しない。

  5. 障害復旧で再露出する

    独立台帳のack・正本が不明なため、古いbackupから復元した公開projectionやobjectへ削除が再適用されない。

  6. 訂正で注目が増える

    公開後の説明・訂正がスクリーンショットやSNS投稿と結合され、削除済みと説明した情報が再燃する。

合格条件

「通常は漏れない」ではなく、失効後取得不能、secret非残存、削除期限内、復元後再露出0件を試験で証明し、失敗時は配布・公開・昇格を停止すること。
