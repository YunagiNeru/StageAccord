DEC-201

モジュール内部の依存方向

承認済み
種別
決定
規範強度
必須
適用範囲
全バックエンドモジュール

各モジュールは api → application → domain の内向き依存とし、infrastructure はapplicationが定義するポートを実装する。domainはSpring、JPA、HTTP、ファイルシステムへ依存しない。

理由と検証

業務規則をフレームワークから分離し、モジュール境界を機械検査できるようにする。ArchUnitで層依存、他モジュールのentity・repository参照、循環依存を拒否する。

DEC-202

識別子と競合制御

承認済み
種別
決定
規範強度
必須
適用範囲
API、集約、永続化

公開識別子はUUIDv7、集約の競合制御は単調増加する64bit version、再実行制御は128bit以上の不透明な冪等キーを使う。

理由と検証

時系列局所性と推測困難性を両立し、状態遷移の取り違えを防ぐ。更新APIは期待versionを要求し、不一致はHTTP 409で現在versionを返す。

DEC-203

APIの表現とエラー形式

承認済み
種別
決定
規範強度
必須
適用範囲
REST／OpenAPI

APIは /api/v1 を基点とするJSON RESTとし、フィールドはlowerCamelCase、時刻はUTCのRFC 3339文字列、エラーはProblem Details形式へ安定した code と correlationId を追加する。

理由と検証

表示用ローカライズと保存値を分離し、クライアントが文言に依存せず例外分岐できる。OpenAPI差分と契約試験で破壊的変更を拒否する。

DEC-204

PostgreSQLの所有境界

承認済み
種別
決定
規範強度
必須
適用範囲
全永続データ

各業務モジュールは専用PostgreSQL schemaとmigration ownerを持つ。通常applicationは共有runtime roleを使い、モジュール境界は公開facade・ArchUnit・repository配置で強制する。テナント境界は workspace_id を含む複合PK・FK・uniqueでDB強制する。

理由と検証

モジュラーモノリスの横断transactionを維持しながら、DB権限で保証できないモジュール境界を誤って主張しない。schema別migration、全tenant FK、別workspace総当たり、他モジュールrepository参照拒否を検査する。

DEC-205

履歴と訂正

承認済み
種別
決定
規範強度
必須
適用範囲
合意、承認、受領、監査、削除台帳

成立済みの合意、承認、受領、監査イベントをUPDATEまたはDELETEで訂正せず、元IDを参照する追加イベントまたは新しい版で訂正する。

理由と検証

過去の意味と操作者を保持する。DBロール制約、トリガー、更新拒否試験、監査連鎖検証で確認する。

DEC-206

外部副作用の確定境界

承認済み
種別
決定
規範強度
必須
適用範囲
メール、Stripe、検査、プレビュー、オブジェクト、監査連携

業務状態とOutboxを一つのDBトランザクションで確定し、外部副作用はworkerがat-least-onceで実行する。送信先は eventId + destination を冪等キーとして重複を無害化する。

理由と検証

DB確定と外部送信の中間失敗で状態を失わない。プロセス強制終了、再試行、逆順、重複配送の統合試験を必須とする。

DEC-207

HTTP操作分類

承認済み
種別
決定
規範強度
必須
適用範囲
全公開HTTP endpoint

HTTP操作をquery、一般command、認証交換、秘密発行、即時失効、冪等中止、非同期削除へ分類し、status code、冪等キー、再試行、response保存、監査を分類ごとに固定する。

理由と検証

DELETEとPOSTへ一律規則を適用すると、即時失効と削除workflow、秘密発行と一般commandが競合する。全endpointが一つの分類へ所属することをOpenAPI lintで検査する。

DEC-208

Web状態の所有境界

承認済み
種別
決定
規範強度
必須
適用範囲
React Web全route

業務状態と認可結果はAPI responseだけを正本とし、WebはOpenAPI生成client、query cache adapter、route loader、局所UI stateに分離する。Webが業務状態を推測または権限を拡大してはならない。

理由と検証

server stateと一時的な表示stateを混同しない。401、403、409、423、503、再読込、別tab更新、read-onlyのE2Eで表示とserver判定を一致させる。

DEC-209

未信頼コンテンツの配布境界

承認済み
種別
決定
規範強度
必須
適用範囲
upload、preview、download、client link

sessionを持つapp originと、upload・preview・download originを分離する。取得はdownload gatewayがgrant secretをPOST bodyで単回交換し、files origin専用の短命HttpOnly cookieを発行して、GET／HEAD／Rangeごとに関係性を再認可しながらAmazon S3からstreamする。browserへS3 URL、object key、AWS資格情報、app session Cookieを渡さない。

理由と検証

直接S3 URLやquery tokenでは発行後の権限失効を再評価できず、履歴、Referer、access logへsecretが残る。grant交換、cookie期限、membership、project grant、auth generation、file visibility失効後のGET／HEAD／Rangeを拒否し、URL・log・historyへのsecret残存が0件であることを検査する。

DEC-210

外部URLの非取得

承認済み
種別
決定
規範強度
必須
適用範囲
ExternalLink

外部URLはserverからDNS解決もHTTP取得も行わない。登録時は構文、http／https、userinfo、literal IP、localhost表記を検査し、遷移時は警告画面と Referrer-Policy: no-referrer を使う。redirect先の安全を保証しない。

理由と検証

redirect検査にはserver fetchが必要となり、非取得方針と競合する。URL parserの変形入力、数値IP、IPv6、userinfo、制御文字を試験する。

DEC-211

監査連鎖の単一append点

承認済み
種別
決定
規範強度
必須
適用範囲
audit event、degraded spool

通常監査は専用DB append functionがchain head行を排他取得し、global sequence、previous hash、event hashを一transactionで付与する。DB停止時はhost別署名連鎖へ記録し、回復後にhost内順序を保持してglobal chainへ追記する。

理由と検証

複数processが同じprevious hashから分岐することを防ぐ。並行append、process kill、複数host spool、再取込、改変を試験する。

DEC-212

Object Lockと削除期限

承認済み
種別
決定
規範強度
必須
適用範囲
Amazon S3 bucket、backup、削除台帳

利用者ファイル、preview、納品成果物のbucketはversioningを有効にするが固定WORM retentionを設定せず、承認済みの法的保持だけを個別適用する。Object Lockは業務本文を含まない監査固定点、削除台帳固定点、通常backupへ用途別期限で適用し、稼働系30日・通常backup35日の削除期限を超えない。

理由と検証

一律Object Lockは削除SLAと競合する。bucket policy、retention、legal hold、delete marker、復元後再適用を試験する。

DEC-213

マルウェア検査モード

承認済み
種別
決定
規範強度
必須
適用範囲
application、worker、ClamAV、Amazon S3

MALWARE_SCAN_MODEはrequiredまたはbypassだけを許可する。requiredはClamAV検査成功を昇格条件とし、bypassはClamAVへ接続せず後続処理を許可するが、ファイルをbypassedとして永続化する。

理由と検証

暗黙の自動フォールバックを禁止し、本番試験の円滑さと未検査状態の追跡可能性を両立する。未設定、空値、未知値、接続障害、モード変更、復元、ロールバックを試験する。

DEC-214

NとN-1の前方互換

承認済み
種別
決定
規範強度
必須
適用範囲
API、event、DB、Web

追加fieldと追加statusはconsumer先行、producer後行で展開し、N-1は未知値を UNKNOWN として読取り可能にする。意味変更と削除は新versionへ分離し、contract gate通過前に旧形式を削除しない。

varchar CHECKだけではJava enumやTypeScript unionの互換性を保証しない。NとN-1の同時起動、新旧event、rollbackを試験する。

  2. 成功responseはprincipal、active workspace、表示用capability、CSRF header token、互換性情報を返す。UIはcapabilityで操作を案内するが、APIはcommandごとに再認可する。

  4. OpenAPIから生成した型付きclientを唯一のHTTP入口とし、cookieはブラウザー管理、CSRF tokenはmemory、相関IDはclientが生成してheaderへ渡す。

HTTP・OpenAPI共通契約

URIや文言ではなく、認証、競合、冪等性、ページング、エラー、監査を全APIで共通化する。

HTTP共通規則
項目契約失敗時
基点/api/v1。業務resourceは複数形、commandはresource配下の名詞で表す。未知versionは404。互換期間外versionは410と移行先を返す。
Content-Type通常は application/json。Problem Detailsは application/problem+json。未対応表現は415、未対応Acceptは406。
認証__Host-stageaccord-session のHttpOnly・Secure cookie。状態変更はCSRF tokenとOrigin検査を追加する。未認証401、認証済みだが不許可403。存在秘匿が必要な他案件は404。
重要操作30分以内の再認証。依頼者の合意・再合意・受領は操作専用15分・単回linkを要求する。AUTH_FRESHNESS_REQUIRED または CLIENT_ACTION_LINK_REQUIRED。
冪等性一律にHTTP methodへ結び付けず、後述の操作分類で決める。一般commandのscopeはactor、workspace、operationId、keyで、request hashと安全な結果を24時間以上保持する。同一key・異なるrequest hashは409 IDEMPOTENCY_KEY_REUSED。秘密・認証response bodyは保存しない。

論理データ設計

PostgreSQLを業務正本とし、schema所有権、複合テナント制約、追記履歴、版固定、保持・削除をDDLへ落とす。

共通カラムと型規則
概念型・カラム制約
識別子id uuid、tenant表は workspace_id uuidapplicationでUUIDv7生成。tenant表は原則 PRIMARY KEY (workspace_id, id)。
状態status varchar(40)PostgreSQL ENUMを使わずCHECK制約。expandで新値を先行許可しN-1共存を維持。
競合version bigint NOT NULL DEFAULT 0UPDATE時に旧version一致を条件とし、成功時に+1。
時刻created_at、updated_at、業務instantは timestamptzDBとapplicationはUTC。表示zoneは別カラム。成立時刻をupdated_atで代用しない。
操作者actor_id uuid、delegated_actor_id uuid NULL削除後も識別可能な不変ID。表示名やemailを履歴キーにしない。
金額amount_minor bigint、currency char(3)負数可否を用途別CHECK。Production V1はJPYだがscaleを業務ロジックへ埋め込まない。
hashSHA-256は bytea 32bytes、外部表現はlowercase hexalgorithm列を持つ場合もProduction V1はsha-256だけを許可。
本文検索対象の短文は text、固定snapshotは jsonb長さ上限をapplicationとDBの両方で検査。監査へ本文を複製しない。
論理削除deletion_status、deletion_requested_at、deleted_at単一の deleted booleanを使わず、独立台帳のterminal hashまで追跡。

  1. Expand

    新しいcipher envelope／digest列、digest_key_id、新key参照を先に追加し、N/N-1の双方が旧形式を読めることを確認する。

  2. Dual read・single write

  3. Backfill

    infra.crypto_rotation.cursorで小分け再開し、行ID・旧key ID・新key IDをAADへ固定する。件数、失敗、旧形式残数を測定する。

  4. Single read

    旧形式残数0、backup復元先で新key復号成功、誤AAD拒否、N-1停止を確認して新形式だけへ切り替える。

  5. Retire

    通常backup35日の復元窓と契約保持backupの復号要件を満たすまで旧keyを破棄しない。破棄後は旧key使用metricが1件でも出たらwriteを停止する。

削除受付と独立台帳ack

  1. 対象集合を固定

    requester、subject、cache／live／backupの対象を認可済みqueryで列挙し、targetSetHashを計算する。DB transactionでcreated request、target、outboxを保存する。

  2. 独立台帳へ冪等追記

    workerはrequest IDとidempotency key digestを送る。台帳は同じkeyへ同じentryを返し、別payloadなら競合として拒否する。送信中はledger_pendingを維持する。

  3. ackを検証

    sequence、previous hash、entry hash、key ID、署名、ack時刻を既知公開鍵で検証し、DBへ保存してledger_ackedへ進める。このcommit後だけAPIは202 Acceptedとrequest IDを返す。

  4. timeoutを閉じる

    規定timeoutまでにackを検証できなければ503 DELETION_LEDGER_UNAVAILABLEを返すが、requestを削除しない。同じidempotency keyで再試行すると保存済み状態を返すか、同じentryを再送する。

  5. 削除と完了証明

    各locationのworkerがreceiptを追記し、cache24時間、live30日、通常backup35日のdeadlineを監視する。承認済みlegal hold対象を除く全receiptとterminal hashが揃った時だけcompletedへ進める。

合意成立処理

  1. commandを固定

    actor、workspace、agreementVersionId、expectedVersion、表示されたcanonical hash、操作専用認証context、idempotency keyを受け取る。

  2. 安全guardを評価

    session／client link、party role、30分または15分freshness、auth generation、time trust、kill switch、agreement statusを順に検査する。

  3. 対象版を再構築

    保存済みcanonical JSONを再正規化し、保存hash、request hash、renderer対象版を比較する。不一致は確定せず409を返す。

  4. party操作を追記

    同じparty・versionの二重操作を一意制約で無害化し、認証時刻、観測時刻、対象hashを保存する。

  5. 成立規則を評価

    ANY、ALL、COUNTのeligible party集合を合意版から読み、現在のacceptanceだけで成立を判定する。

  6. 状態と副作用を確定

    成立時だけagreementをacceptedへ変更し、AgreementAccepted と監査eventを同一transactionのOutboxへ書く。project生成は購読側が冪等に一度だけ実行する。

チェックポイント進行処理

提出

前段locked、actor assignment、必須item完了、全fileがreadyまたは許可済みexternal URL、expectedVersion一致を検査し、提出snapshotを固定する。

修正

通常コメントはquotaを消費しない。正式roundだけを一回として数え、仕様不一致訂正は別classification、追加変更はaccepted change orderまで作業scopeへ入れない。

承認

対象file・submission version、approval rule、各party action、time trustを固定し、未操作を承認へ変換しない。

固定

approval成立後にcheckpointをapprovedからlockedへ進め、次のcheckpointだけをactivateする。訂正は新submissionまたはchange orderとして追記する。

日程再計算

  1. 基準を選ぶ

    合意済みcalendar snapshot、現在の未着手checkpoint、遅延・保留・変更注文の発生点を読み取る。

  2. 営業日を加算する

    IANA time zone、稼働曜日、休日、独自休業日、締切時刻を使い、未来かつ未着手の予定だけを順に計算する。

  3. 案として保存する

    旧日程、新日程、理由、影響checkpoint、最終納品変更有無を schedule_proposal に保存し、projectへ直接反映しない。

  4. 必要な承認を取る

    最終納品日が変わる場合は契約責任者の明示承認後、そうでない場合もcreator確認後に適用する。過去と着手済み予定は保持する。

取込処理

  1. Initiate

    actor、workspace、project、checkpoint、用途、表示filename、declared media type、sizeを検査し、ChecksumAlgorithm=SHA256でCreateMultipartUploadを呼ぶ。sizeは1..4,000,000,000、part sizeは67,108,864、最大60、期限24時間。Amazon S3疎通不能、host一時領域90％、required時のscanner定義24時間超、plan上限時は開始しない。

  2. Sign and upload part

    part番号、expected size、object key、upload ID、x-amz-checksum-sha256を固定したSigV4 URLを15分で発行する。browserはAmazon S3へ直接PUTし、ETagとchecksumをアプリへ返す。methodはPUTだけ、List・Delete・Complete・別key・clean bucketの権限を含めない。

  3. Complete

    全part番号の連続性、最終part以外64MiB、各ETag、各SHA-256 checksum、合計size、upload owner、project stateを再検査し、appだけがpart checksum一覧を付けてCompleteMultipartUploadを呼ぶ。結果のobject version IDをDBへ固定する。

  4. Fetch and hash

    workerは12GiB暗号化一時領域へstream取得し、noexec・nodev・nosuid、同時1件、CPU 2、memory 8GiB、30分上限で実sizeとSHA-256を測る。

  5. Apply scan mode

    requiredではオンプレ専用ClamAV hostの暗号化・接続元制限済みTCPへINSTREAMで全本文を送り、engine、定義版、config hash、bytes read、bytes scanned、resultを記録する。byte数一致かつ陰性だけをcleanとする。bypassではClamAVへ接続せず、BYPASSED、構成hash、処理時刻、correlation IDを記録して後続へ進む。

  6. Promote

    quarantineから受入用cleanバケットへAmazon S3 server-side copyし、コピー先version ID、size、全体SHA-256、scan statusを照合してreceiptを保存する。不一致、遅延、read不能はpromotion_pendingを維持する。バケット名をscan verdictとして扱わない。

  7. Preview

    許可形式だけをnetworkなし、non-root、read-only root、capabilityなしのsandboxで処理する。変換失敗時もFileVersionがreadyでscan statusが配布可能ならpreviewCapability=unavailable、downloadCapability=allowedとし、元fileの検査状態を変更しない。

  8. Distribute

    app.exampleでgrantを発行し、POST bodyでfiles.exampleへ交換して同host限定・短命・HttpOnly cookieを設定する。gatewayはGET／HEAD／各Rangeごとにproject関係、file visibility、auth generation、FileVersionのready、運用モードで許可されたcleanまたはbypassed、昇格receiptを再認可し、自身がstreamする。Amazon S3 URL、AWS credential、app session cookieをfiles originへ渡さない。

監査の原子追記とspool統合

  1. DB追記

    audit_owner（NOLOGIN）が所有するSECURITY DEFINER audit.append_event(canonical_payload, actor, correlation_id)だけを入口とする。functionはSET search_path = pg_catalog, auditを固定し、呼出し側roleのsearch pathと同名objectを参照しない。runtime roleはbase tableを直接SELECT／INSERT／UPDATE／DELETEできない。

  2. 入力を正規化

    function内部で許可field、型、UTF-8、最大64KiBを検査し、RFC 8785 canonical JSONを再生成する。呼出し側が渡したhash、sequence、previous hashは受理しない。

  3. 連鎖を原子更新

    advisory transaction lockを取得し、直前sequence／hashを同じtransactionで読取り、新sequence、previous hash、event hashを計算して一件だけINSERTする。canonicalization、INSERT、業務commandのどれかが失敗したらtransaction全体をrollbackする。

  4. 同時実行

    一意制約 (sequence) と (event_id)、直前hash一致制約により競合を直列化する。transaction失敗時は業務commandもrollbackし、監査なしの成功を返さない。

  5. 緊急spool

    DB全体が利用不能で、かつ事前承認された復旧操作だけは、監査専用のGit管理外平文ファイルから読み込んだEd25519鍵で hostId + bootId + monotonicSequence + observedAt + monotonicTime + payloadHash を署名し、暗号化append-only spoolへ書く。一般業務commandは停止する。

  6. 統合

    DB回復後、host署名とhost内sequence連続性を検証し、observedAt、hostId、bootId、monotonicSequence の安定順にmergeする。取込eventは元時刻とhost sequenceを保持し、新しいDB sequenceを付与する。

  7. 検証

    各spool recordと取込recordの対応hash、未取込件数0、terminal hash、日次署名を二者確認するまでruntimeをrecovery_verificationから戻さない。曖昧な順序を隠さずorderingConfidenceを記録する。

交換host復旧と再露出防止

  1. 書込みを止める

    重大incidentを二者で宣言し、public入口を保守表示へ切り替える。auditはdegraded spoolを含め継続する。

  2. 故障hostを隔離する

    公開VIP、管理route、DB／Valkey接続元、Amazon S3 credentialを故障hostから剥奪し、再接続不能を実測する。diskを再利用する場合は消去証拠を残す。

  3. 交換hostを構築する

    承認済みOS、container runtime、digest固定image、Git管理外設定ファイルを適用し、所有者・mode・秘密値非出力を起動前検査する。

  4. 一貫復旧点を選ぶ

    既存PostgreSQLの復旧点、Amazon S3 file manifest、trust manifest、deletion ledger terminal hash、backup catalogを照合する。不一致は公開不可とする。

  5. 失効と削除を再適用する

    影響したsession、client link、support grant、recovery code、download grant、秘密を失効し、独立台帳をDB、projection、Valkey、Amazon S3、通知queueへ再適用する。

  6. 限定公開する

    運用者read、代表write、audit chain、Outbox、required／bypass各file flow、download、backupを確認し、一般trafficを段階的に戻す。

  7. 目標値を測定する

    障害発生から復旧までの実測RPO・RTOと可用性を記録し、証拠が蓄積するまで保証値として扱わない。

    unit、module integration、API contract、認可、E2E、async fault、file securityを実行する。

    backup age、隔離restore、migration N/N-1、rollback image、TLS、ClamAV、runtime guard、署名を検査する。
